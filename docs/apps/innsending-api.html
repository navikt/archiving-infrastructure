Submission core

innsending-api

The central backend for work-in-progress applications, attachment files, PDF work, submission handoff, archive feedback, and cleanup.

Type
Core backend
Runtime
Kotlin and Spring Boot
Metadata
PostgreSQL
Files
Google Cloud Storage

Nearly every digital user path converges here. innsending-api owns temporary submission state and file storage, but final archiving belongs to soknadsarkiverer and Joark.

What it does

  • Creates, reads, updates, and deletes applications and attachment metadata.
  • Stores uploaded files, scans them with ClamAV, and supports PDF generation and merging through Gotenberg.
  • Supports FyllUt, SendInn, ettersending, and no-login request variants.
  • Calls soknadsmottaker when the user submits and later serves file bytes to soknadsarkiverer.
  • Consumes archive feedback, publishes user notifications, and runs cleanup and archive-verification jobs.

Data lifecycle

Application, attachment, event, and configuration metadata lives in PostgreSQL. File bytes live in Google Cloud Storage. Data is temporary: scheduled jobs remove old drafts and submitted material after archiving or expiry. Joark is the long-term archive.

What it does not do

It does not render citizen interfaces and does not create the final Joark journal post. It provides the durable handoff point between user interaction and asynchronous archiving.

Technical details

  • Kotlin, Spring Boot, Java 21
  • Maven modules for API, service, and external clients
  • PostgreSQL 15 and Flyway
  • Google Cloud Storage
  • REST and Kafka
  • TokenX and Azure AD
  • NAIS autoscaling on GCP
