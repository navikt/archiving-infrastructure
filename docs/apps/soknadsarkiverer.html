Archive worker

soknadsarkiverer

Consumes submitted metadata, fetches the files, prevents duplicate journal posts, writes to Joark, and sends the result back.

Kotlin and Spring Boot

soknadsarkiverer owns the asynchronous work required to turn references and metadata into a permanent journal post. Its retry and state handling isolate external archive failures from the citizen's original request.

What it does

  • Consumes logged-in and no-login submission messages from Kafka.
  • Tracks received, started, archived, finished, and failure processing states.
  • Fetches referenced file bytes from innsending-api.
  • Queries SAF by external reference to detect earlier archiving.
  • Creates a journal post and documents through the Joark API.
  • Publishes archive feedback, processing events, and metrics.

Failure behavior

Transient failures use increasing retry delays. Once the retry plan is exhausted, the task reaches failure and soknadsarkiverer publishes a negative response. Already archived submissions and already-deleted files have dedicated handling because retrying them is not useful.

What it does not do

It does not receive browser uploads or own temporary file storage. It starts after soknadsmottaker has accepted and published the metadata.

Technical details

  • Kotlin, Spring Boot 4, Java 21
  • Kotlin coroutines
  • Kafka consumption and publishing
  • Generated innsending-api client
  • GraphQL client for SAF
  • REST client for Joark
  • Azure AD client credentials
  • JWT-protected admin API
