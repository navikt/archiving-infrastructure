Overview / System flow

End to end

How information moves through the system

There are two main flows to understand. Form definitions move from authoring to the FyllUt runtime. User submissions move through temporary storage and Kafka before they reach Joark.

Flow 1: publish a form

This flow changes what FyllUt can render. It does not submit citizen data.

1

Build in Bygger

A form builder edits form.io definitions, translations, and recipient information. Bygger reads and writes this material through forms-api, which persists it in PostgreSQL.

2

Publish to GitHub

Bygger backend writes the selected form JSON, translations, and resources to skjemautfylling-formio. It also pins the skjemabygging-formio commit that contains the FyllUt application code.

3

Build the production image

skjemautfylling-formio builds on the pinned FyllUt base image and adds the published content. The result is one deployable image with application code and form content.

4

Render in FyllUt

Citizens open FyllUt and receive the published form. Development and preproduction may read forms directly from forms-api, but production uses the GitHub-bundled content.

Two sources can look authoritative

forms-api stores editable form data and publication metadata. Production FyllUt currently renders content bundled from skjemautfylling-formio. Keep that distinction in mind when a form differs between staging and production.

Flow 2: choose a user path

The route depends on what the user needs to send. All digital routes converge on innsending-api.

New form

FyllUt renders the form, uploads its attachments through innsending-api, and submits the completed application. The user stays in FyllUt throughout the current flow.

Additional documentation

fyllut-ettersending helps the user identify the existing form or case and choose paper or digital delivery. The digital route creates an ettersending in innsending-api and redirects to SendInn for file upload and submission.

SendInn document submission

SendInn handles digital ettersending and document-only submission. It also lets a user finish an old FyllUt draft when attachments were previously uploaded in SendInn. Its server proxies calls to innsending-api with a TokenX token.

Paper route

FyllUt and fyllut-ettersending can direct users to a paper process. That branch does not use the full digital upload and Kafka path described below.

Flow 3: submit and archive

Files stay in innsending-api until the archiver asks for them. Kafka carries metadata and status, not the uploaded file bytes.

1

Work in progress

innsending-api stores application and attachment metadata in PostgreSQL and file content in Google Cloud Storage. It also scans uploads with ClamAV and supports PDF generation and merging.

2

Submission handoff

When the user submits, innsending-api calls soknadsmottaker over REST with application and document metadata.

3

Kafka intake

soknadsmottaker maps the request to an InnsendingTopicMsg and publishes JSON to the logged-in or no-login Kafka topic. This keeps user-facing submission separate from archive processing.

4

Enrich with files

soknadsarkiverer consumes the message and fetches the referenced files from innsending-api over an Azure AD protected REST endpoint.

5

Check and archive

The archiver queries SAF by external reference to avoid duplicate journal posts. If no prior archive entry exists, it sends a journal post and documents to Joark.

6

Report the outcome

soknadsarkiverer publishes success or failure feedback to Kafka. innsending-api consumes it, updates the submission state, sends user notifications where relevant, and later cleans up temporary data.

Failure and retry path

soknadsarkiverer tracks each submission through received, started, archived, and finished states. Transient failures are retried with increasing delays. A submission reaches failure after the retry plan is exhausted, and the negative result is sent back to innsending-api. Duplicate archive entries and already-deleted files have separate handling because repeating the same work would not help.

Operations are visible from innsending-admin

Nav staff can inspect archive status, rerun a stuck submission, trigger maintenance jobs, check attachment availability, and manage selected innsending-api configuration. The admin UI does not access databases or buckets directly.

The primary Kafka payload is JSON

soknadarkiv-schema still contains shared Avro records and supports legacy processing-event and metrics compatibility. The current primary submission message between soknadsmottaker and soknadsarkiverer is plain JSON. Older repository descriptions may not make this migration clear.
