Felles mønstre

NAIS og GCP

Applikasjonene som deployes, kjører på NAIS. innsending-api oppretter også Cloud SQL og Google Cloud Storage.

Autentisering etter målgruppe

Brukerrettede tjenester bruker ID-porten og TokenX. Ansattverktøy bruker Azure AD eller Entra ID. Ved tjenestekall brukes Azure AD client credentials eller OBO-token.

REST før Kafka

Brukerrettede klienter kaller synkrone REST-API-er. Etter innsending går metadata via Kafka. Arkiveringen og eventuelle nye forsøk kan dermed fortsette etter at brukeren har fått svar.

OpenAPI-kontrakter

Flere tjenester genererer API-grensesnitt eller klienter fra OpenAPI. Når du endrer en kontrakt, sjekk tjenesten som implementerer den og de genererte klientene som kaller den.

Midlertidige og permanente data

innsending-api lagrer søknader og filer midlertidig. Joark lagrer den permanente journalposten. SAF tilbyr arkivoppslag.

Ende-til-ende-tester

archiving-infrastructure tester hele arkiveringskjeden. Med arkiv-mock kan testene gjenta scenarioer med vellykket arkivering, feil, forsinkelser og duplikater.

Før du endrer en felles flyt

Finn tjenesten som eier dataene, og de genererte klientene og asynkrone konsumentene som bruker dem. Bestem rekkefølgen for deployment. Sjekk hvordan publiserte skjemaer blir tilgjengelige i FyllUt, og hvordan REST-innsendinger blir Kafka-meldinger. Skill dagens JSON-meldinger fra eldre Avro-poster. Sjekk også hvordan tilbakemeldinger fra arkivet påvirker opprydding og brukervarsler.
